# Upstream RISC-V KVM SDK

This branch keeps QEMU, Linux, OpenSBI, dtc and kvmtool at the upstream commits in
`conf/kvm/sources.json`. The source URLs are upstream URLs; the gitlinks pin exact
versions. There are no research patches or automatic floating branch updates.
The host runs Buildroot; the inner guest runs Buildroot or Debian 13.

## Dependencies and build

The delivery branch is `sdk-kvm-upstream` in the team repository.
Clone it explicitly; the research branches have different build/test targets:

```sh
git clone --branch sdk-kvm-upstream --single-branch https://github.com/riscv-pgtlb/riscv-spike-sdk.git
cd riscv-spike-sdk
```

All commands below run in this branch's SDK root on the Linux build server.

Use an x86-64 Linux build server with Git, Make, Python 3.10+, a C/C++ toolchain,
cpio, gzip, pkg-config, bison, flex, bc, OpenSSL/ELF development libraries and
QEMU's GLib/pixman/slirp development dependencies. QEMU may download its pinned
subprojects. A RISC-V Linux cross compiler is needed for the kernel/firmware/lkvm.

For Ubuntu 22.04/24.04, an administrator can install the usual dependencies:

```sh
sudo apt-get install build-essential git python3 python3-venv python3-pip \
  ninja-build pkg-config cpio gzip bison flex bc libssl-dev libelf-dev \
  libglib2.0-dev libpixman-1-dev libslirp-dev zlib1g-dev \
  rsync file wget curl unzip xz-utils perl
```

These packages do not provide the RISC-V cross compiler. Use an installed RV64
Linux toolchain with static C libraries (for example the toolchain generated by
the base Buildroot build). A bare-metal `riscv64-unknown-elf-` compiler will not
work for lkvm. The existing server's absolute paths are examples of local inputs,
not paths that are expected to exist on another machine.

```sh
set -e                                 # stop if a download/build fails
make kvm-prepare                       # initialize only the five KVM submodules
```

Choose **one** input route. Route A builds the base user space and downloads the
external toolchain selected by the pinned Buildroot configuration:

```sh
set -e
git submodule update --init --depth=1 -- repo/buildroot
make rootfs-base
sdk_cc=$(find "$PWD/rootfs/buildroot_initramfs/host/bin" -maxdepth 1 -name "*-gcc" -print -quit)
test -n "$sdk_cc"
export CROSS_COMPILE="${sdk_cc%gcc}"
```

Route B supplies existing inputs (replace both paths with real local paths):

```sh
export CROSS_COMPILE=/absolute/path/to/riscv64-linux-
export BASE_ROOTFS=/absolute/path/to/rootfs.cpio.gz
```

Then continue with either route:

```sh
set -e
make kvm-check                         # fail early on wrong/missing inputs
make kvm-build KVM_JOBS=4
make kvm-verify
make kvm-test-static
make kvm-test
```

The compiler is selected with CROSS_COMPILE; it is not rebuilt implicitly.
`kvm-check` checks build commands/development packages, pinned component state,
static RV64 compiler output, and the required base-rootfs files and BusyBox
architecture. The full build runs the same check before compiling components.
It cannot guarantee future download availability or verify every dynamic library
inside an externally supplied rootfs; the runtime tests remain necessary.
All KVM outputs are isolated in `build/kvm/`. Kernel modules use a matching
`-sdk-kvm` kernel release. Dtc and kvmtool build in private clones so the pinned
submodule working trees stay clean. Keep the submodule object stores available
until builds finish. No kernel, QEMU or firmware binary is borrowed from the
research branch. The manifest checks source pins, build inputs and output hashes.
The ordinary KVM kernel starts from the upstream RISC-V defconfig and applies
`conf/kvm/linux.fragment`, rather than enabling unrelated distribution drivers.

Individual targets: `linux-build`, `opensbi-build`, `qemu-build`, `kvmtool-build`
(also builds libfdt), and `kvm-pack`. After changing a build input, rebuild its
component and repack before verifying/running. `rootfs-kvm` builds Linux/lkvm and
packs the rootfs; a full `kvm-build` also builds firmware and QEMU.

## Run and stop

```sh
make run-kvm-host
# Login root on the outer Buildroot host, then:
run-guest
```

The inner guest uses one vCPU, 256 MiB and no networking. `poweroff` returns to
the outer host. Ctrl+A, release, then X exits the outer QEMU.

`make kvm-test` automatically logs into the host, loads KVM, starts the ordinary
guest, checks guest memory and time progression, shuts it down and checks host
return. Only the explicit `sdk_regression=guest` boot flag enables automatic
guest tests/shutdown. Results are saved in `build/kvm/logs/regression-*/` with
the console, manifest snapshot, SDK commit/status, result and SHA256SUMS.
This is an ordinary KVM smoke test, not a security or performance benchmark.

For Debian use `make run-debian-host DEBIAN_DISK=/absolute/path/to/debian-guest.raw`
and run `run-debian` in the outer host. See [Debian setup](debian-guest.md).
The disk remains independent of the initramfs; never share a writable disk
between running VMs. Network/apt tests are separate from the diskless regression.

For an automated Debian user-space smoke test:

```sh
make kvm-test-debian DEBIAN_DISK=/absolute/path/to/debian-guest.raw
```

This uses a temporary QEMU disk snapshot and `init=/bin/sh`, checks Debian 13,
RISC-V, file I/O and command execution, powers off the guest and checks host
return. It does not require a password or alter the original disk. It does not
test normal systemd login, network or apt. Evidence is under
`build/kvm/logs/debian-smoke-*/`.

Current validation is recorded in [KVM validation](kvm-validation.md).
The original Spike targets remain present but have not been retested in this
KVM work. A clean-machine build including compiler and base user space is also
separate from a component build using an existing compiler/base initramfs.

## Download and startup troubleshooting

- Do not use `git submodule update --init --recursive` for this workflow. KVM
  needs only the five components selected by `kvm-prepare`; Buildroot is optional
  if a suitable base is supplied. Downloading the entire GNU toolchain repository
  is unnecessary when a compiler is already installed.
- If a submodule is already initialized at another revision, preparation stops.
  Preserve any edits first, then update only the named paths with
  `git submodule update --init -- repo/linux repo/qemu repo/opensbi repo/dtc repo/kvmtool`.
- For TLS/RPC/early-EOF download failures, stop and retry the failed operation.
  `git -c http.version=HTTP/1.1 submodule update --init --depth=1 -- repo/qemu`
  is an example for QEMU. A proxy on your laptop does not automatically proxy
  downloads made by the Linux server. Do not delete existing repositories to retry.
- A compiler prefix ends in `-`, not `gcc`. If static linking fails, install the
  matching static C libraries or select a complete RV64 Linux toolchain.
- `kvm-pack` needs Linux, modules, lkvm, QEMU and firmware outputs. For the first
  build use `kvm-build`; individual targets are for subsequent component rebuilds.
- After editing packaged scripts or build inputs, rebuild the affected components
  and run `kvm-pack`; checksum errors intentionally prevent booting stale images.
- For Debian HTTPS errors, check `date -u` inside Debian against the build server.
  A guest started with `init=/bin/sh` does not run normal time synchronization;
  certificates and signed APT metadata require a correct clock. Correct the clock
  instead of disabling TLS, signature, or metadata validity checks.
